## Direction mapping and transform

Packed in the canonical order `front(S) / back(N) / left(W) / right(E)` at destCells
`[0,0] [1,0] [2,0] [3,0]`.

The only transform is placement: `trim: alpha`, `anchor: center_bottom`, **`fit: fixed` with
`scale: 1.0` on every direction — no resampling occurs.** PixelLab authored the figures at
44–45 px, the runtime content height, so every runtime pixel is exactly as generated.

now recorded in the lock's §7 source-generation contract.

## Residual observations for the reviewer

- **Identity drift from the previous canonical Mage.** The tunic is **teal, not blue**, and the
  chest gem reads as a pale pendant rather than a green diamond. Three prompt/parameter attempts
  failed to move it — `force_colors` constrains the palette but not which colour lands on which
  garment. Adopting this family therefore **redefines the Mage's canonical identity**. That is an
  art-direction decision and is the reviewer's to accept or reject.
- **Camera is eye-level**, as permitted by lock v2.0. There is no meaningful downward pitch,
  foreshortening or visible top surface. Correct under v2.0; would have failed v1.1.
- Cross-direction identity, scale and grounding are strong — the same character reads in all four
  cells, which is what v2.0 actually gates on.
- Upper-left key light is not directly controllable by the provider and was not enforced; judge it
  visually.
- Browser/iPad runtime behaviour is unevaluated by design: nothing is integrated.
