## 2026-07-26 — ACTION casts: the button now does something almost everywhere

- Author/branch: Claude Code, `claude/action-feel`, stacked on `claude/village-shop-structure` ([PR #143](https://github.com/Galashots/eldoria-v2/pull/143)). Owner-requested 2026-07-26 ("make it FUN"), replacing a planned Farm-anchor art-integration pass that the owner correctly redirected away from after I noted that props make the game look finished without making it more fun.
- The defect, which was a feel defect rather than a bug: pressing ACTION anywhere outside the `sx(42)` = 84 world px walk-up range ran `heroPresentation.playAction()` and **nothing else** — the cast animation played, no projectile left the hero, no sound fired, and nothing in the world reacted. On a 1920×1280 map that is what the primary verb did almost everywhere, and it is most of why the game read as walking between dialogue boxes.
- Scope: ACTION now fires a ranged cast when nothing is interacted with. `src/systems/castTargeting.ts` is the Phaser-free rule (direction, a 192 world px / three-tile range, a ±56 px corridor, and an explicit castable-id set); `src/presentation/CastSparkController.ts` is the visible half — projectile, sparse trail, impact ring and sparks, a 90 ms/0.0035 camera shake on a hit only, and a 260 ms cooldown so a held button cannot fill the screen. Built entirely from primitives and tweens like every other effect in the scene: **no new art and no new audio**. The Mage throws a round arcane spark, the Ranger a thin arrow, each in its own accent colour. `HeroPresentationController` gained `currentFacing()`, since the scene drove facing but had never read it back.
- **The design rule, and why it is a rule:** a cast reaches things you would *hit* — the Practice Slime, the three Sleepy Sprouts, the Mossy Stone — and never anyone you would *talk to* (Mira, Baker Pell, the Notice Board, the Village Well) or a bonus you harvest by hand (the Crop Patch). A spark that opens Mira's dialogue from three tiles away reads as a bug and would let a player skip the walk the objective is asking for; dialogue and quest handoffs also assume the hero is standing at the target. Keeping them out of range is what leaves quest routing, objective state and save behaviour completely untouched. A ranged hit runs the **same** interaction handler a close hit does, so the cast changes reach and nothing else.
- **A regression this introduced and the smoke suite caught.** The first version gated `tryInteract()` behind `nearestTarget()`, assuming that skipping it when nothing was near could not matter. It silently broke **every Wildbloom secret reveal on both profiles**: `PolishedWorldScene` wraps `tryInteract` to check the Wildbloom spots first, and those spots are not interaction targets, so gating the call skipped them entirely. Types were clean and the new tests passed. `tryInteract()` is now always called. The obsolete `Nothing to use here yet.` toast is removed with it — it fired on every cast and read as an error message for a working action, and nothing asserted it.
- Tests: `tests/unit/castTargeting.test.ts` (15 assertions) covers the rule as pure logic — direction vectors, range and corridor bounds, nearest-of-several, flying past a non-castable target to reach a castable one behind it, and the castable/non-castable split asserted by name in both directions. `tests/cast-action.spec.ts` (6 browser tests, both profiles) is the wiring gate: a cast hits the slime from 150 px (beyond the 84 px walk-up reach), a cast into empty ground changes nothing and raises nothing, and a cast does **not** advance Mira from range while walking up to her still does. That last test initially failed for the wrong reason — it probed `dialogueBox.isOpen()`, but Mira advances the farm quest on a fresh save rather than opening a dialogue — so it now probes the objective line instead.
- Verification (exact final head): `npm run check` (exit 0); `npm run test:unit` (322/322, +15); `npm run test:visual-targets` / `test:asset-pipeline` / `test:terrain-blend` (pass); `npm run smoke` (105/105, +8). Every exit code captured directly rather than through a pipe. Durable evidence is one two-profile contact sheet at 1194×834 plus measurements and a written note: [`docs/playtests/2026-07-26-cast-action/`](playtests/2026-07-26-cast-action/).
- Compatibility: no save schema, profile ID, curriculum, quest, reward, interaction ID, map data, dependency, or workflow change. Two behaviour changes beyond the new cast: the empty-press toast is gone, and interactions on castable targets are now reachable at up to 192 px instead of 84 px.
- Remaining risk: the cast is expression and reach, not yet a loop — the Practice Slime is still a one-time encounter, so after it is defeated there is little on the Farm to cast at. Gold still has no sink. Whether a seven-year-old finds this fun is the one thing no gate here can answer; a real playtest remains outstanding and unclaimed.

## 2026-07-25 — Eldoria Village's first structure: Baker Pell's shop

- Author/branch: Claude Code, `claude/village-shop-structure`, **stacked on `claude/world-depth-ysort`** ([PR #142](https://github.com/Galashots/eldoria-v2/pull/142)) because the structure sorts in that PR's actor band. **Verdict: `HOLD` — `named_next_gate: owner (Leo) visual verdict.`** Claude does not self-approve art or composition. The render-layer question this PR opened is now settled by owner decision (below); the visual verdict on the composition itself is still outstanding.
- Why now: `docs/art-pipeline/review/village_top_gaps/AUDIT.md` records nine approved runtime masters across three shop-facade families (wall `stone_base`/`wood_trim`/`window_lit`, door `closed`/`highlighted`/`open_optional`, roof `thatch_base`/`thatch_moss`/`ridge`) that had never been loaded by the game, and its own scope boundary states that "Map 3 composition remains Claude's separate responsibility". The Village had no structures at all; Baker Pell stood in an empty field.
- Scope:
  1. `scripts/compose-village-shop-tileset.mjs` concatenates the three already-gated family sheets in the audit's fixed order and upscales 2x nearest-neighbour into `public/assets/tilesets/tile_village_shop.png` (288×32, nine 32×32 cells) — zero derived pixels, the same convention `compose-farm-scatter-tileset.mjs` uses. Each input sheet's SHA-256 is asserted against the value recorded in the audit, so the runtime sheet is pinned to the exact approved art and a drifted master fails loudly instead of shipping unapproved pixels. A sidecar `assets/tilesets/tile_village_shop.cells.json` records the packed frame order; both new files join the `test:generated-surfaces` diff gate.
  2. `src/data/villageShopBuilding.ts` declares the composition as Phaser-free data (four cells wide, four tall, at Village tiles 8..11 × 1..4) and resolves it to world-space placements, a ground line, a solid rect and an overhang rect. Placement is derived from Baker Pell's own map position rather than chosen freehand: the shop sits directly up-map of him with its door in his column, so the shopkeeper stands in front of his own door.
  3. `WorldScene` renders the cells on the Village only, all sharing one depth taken from the structure's ground line (the bottom edge of its last row) in the shared actor band, plus one invisible static body for the solid block. **Only the bottom two rows are solid**; the two roof rows overhang walkable ground, which is what makes being hidden by the roof possible — a structure whose sprite exactly covers its collision footprint can never occlude anything. No Tiled tileset, no gid, no map JSON edit.
- **Owner decision, 2026-07-26 (Leo, in session): structures are actors, not terrain.** The composition was submitted with the render-layer question open — the shop families declared `renderLayer: "terrain"`, which draws beneath every actor and therefore cannot occlude the hero — and rows 2 and 3 of the evidence sheet showed the same frame under both choices. The owner chose the sorted treatment **and generalized it to every building going forward**. Applied as: a new rule in [`docs/VISUAL_ASSET_CONTRACT.md`](VISUAL_ASSET_CONTRACT.md) "Buildings and props" (structures declare `actors_body` and Y-sort by ground contact; a structure's solid footprint covers only the rows it occupies, so art above it overhangs walkable ground); the shop **wall and door** targets corrected from `terrain` to `actors_body`; and the `VILLAGE_SHOP_SORTS_AS_ACTOR` escape hatch deleted, since a settled decision does not need a toggle. Notably this **generalized an existing convention rather than inventing one** — `farm_vegetation_targets.json` and `farm_props_targets.json` have declared `actors_body` for tall trees, bushes, rocks, fences and gates all along, with notes explicitly deferring the Y-sort implementation. That implementation is the sibling PR #142. New unit gates assert the shop families stay `actors_body` and that those tall-object families have not split away from it.
- **Correction to a claim first published in this entry.** I reported that `tile_village_shop_roof` had no declared target. It does: `docs/visual-targets/village_shop_roof_target.json`, git-tracked, asserted by `scripts/test-village-art-top-gaps.mjs`, and read by `validate:visual-targets` (which scans every JSON in the directory). I had only looked in `farm_village_tile_targets.json` and concluded from its absence there that no target existed. **All three shop families now declare `actors_body`.** The unit gate has been widened from one file to the whole target directory, since a gate scoped the same way as my own blind spot could not have caught this. **The real loose thread** is narrower and still open: the roof target declares `collision.solid: true`, while the composition deliberately makes only the bottom two rows solid so the roof overhangs walkable ground and can occlude the hero — a roof solid on its own would remove the overhang and with it the occlusion. Reconciling the per-tile declaration with the composition is an owner question, recorded in the target's own notes.
- **Save compatibility defect found by self-audit, and fixed.** The structure is new, so a save written before it existed can restore the hero onto ground it now occupies. An Arcade static body only blocks a body *moving into* it and never ejects one that already overlaps, so the hero simply stood inside the building — reproduced at Village world (640, 256), dead centre of the solid block, on both profiles. `pushClearOfSolid` now moves an overlapping body down-map clear of the block once at scene create (down-map deliberately: that is the door side, where the hero was heading anyway). Two browser regressions restore a v2 save inside the footprint and assert the hero ends up outside it and can still walk. Note the rect is derived from the sprite plus the body's configured size/offset rather than read from `body.left/top`: Arcade recomputes those during its own step, so at create() time they still described a body at the origin and the first version of this fix silently did nothing.
- Verification (exact final head): recorded in the PR body. Durable evidence is one two-profile contact sheet at 1194×834 plus a layout/measurement note: [`docs/playtests/2026-07-25-village-shop/`](playtests/2026-07-25-village-shop/).
- Compatibility: no save schema, profile ID, curriculum, quest, reward, interaction ID, map JSON, dependency, or workflow change. Baker Pell's interaction is untouched. The Village gains one solid 4×2-tile obstacle up-map of the road; the road itself and every existing route stay unobstructed (asserted).
- Remaining risk: the ridge row can render behind the header HUD bar when the camera clamps at the map's top edge and the player is beside the shop — recorded in the evidence README with the one-constant alternative. The shop is the Village's only structure, so it reads as isolated rather than as part of a street. Physical-iPad and child validation remain outstanding and unclaimed.

## 2026-07-25 — World actors sort by ground contact instead of fixed depths

- Author/branch: Claude Code, `claude/world-depth-ysort`, built forward from `main` at `30e4467` (PR #137 merged). Owner-requested on 2026-07-25, outside the `PLAYTHROUGH_UI_AUDIT_2026-07-23` queue, as the cheap half of a rejected isometric conversion.
- Scope (presentation only): the hero, the Practice Slime, and Mira's silhouette each sat at a hardcoded render depth — 3, 2 and 3.5. A fixed order is correct from exactly one side and wrong from the other, and both errors were live: the hero drew **in front of the Practice Slime while standing up-map of it**, and **behind Mira while standing down-map of her**. New `src/systems/worldDepth.ts` defines one actor depth band, `[2, 3.5]`, sorted by ground-contact y at 0.001 depth per world pixel, sitting between the ground-shadow layer (1) and the floating quest-indicator layer (4+), both unchanged. `HeroPresentationController.syncDepth()` re-sorts the hero (and, for the Ranger, its two accent Graphics layers, held a quarter-pixel either side of it) from `syncPosition()` every frame; the two static actors sort once at creation. The hero's ground contact is read from its physics sprite's displayed bottom, which is the same line both profiles are drawn on — the Ranger renders as that sprite and the Mage's bottom-origin sprite is offset onto it.
- **No occluders exist yet.** The maps' Decor tile layers hold a handful of tiles and no tall props, so today this repairs those three actor orderings and nothing more. Its larger value is as the prerequisite: an occluding tree or shop front cannot be walked behind without it.
- **Band purity (self-audit repair).** Three objects still rendered at a fixed depth *inside* the new band, which makes their layering depend on where on the map an actor happens to be standing rather than on any decision: the screen-fixed ambient dust motes (2 → **1.5**, still above the ground shadows and below every actor) and the crop-bonus burst with its four leaves (3 → **6**, joining every other interaction VFX — affordance rings at 6, slime strike bursts at 8, Wildbloom reveals). Both had been given their old values back when the hero was itself pinned at a fixed 3. The band now holds actors and nothing else, and a source-level unit gate scans `src/scenes` + `src/presentation` and fails on any future `setDepth()` literal inside `[2, 3.5]`. Confirmed red against the pre-repair source (it flags exactly those three call sites).
- **A false comment, also from the self-audit.** The Practice Slime's new sort carried a comment claiming the slime never moves. It does — `PracticeSlimeEncounterController.playSlimeReaction` tweens it up and sideways on every strike. The tween yoyos back to exactly its original position, and a mid-hop slime is airborne, so sorting it once at creation is *right* rather than merely adequate; re-sorting it off the ground would briefly order it as though it stood further up the map. The comment now says that.
- Tests: `tests/unit/worldDepth.test.ts` (17 assertions) covers monotonicity, band containment and clamping, non-finite fallback, the epsilon being finer than one world pixel (so accent layers can never reorder two actors), both repaired orderings at the Farm's real slime/Mira coordinates, `spriteGroundY` agreement between the centre-origin Ranger sprite and the offset bottom-origin Mage sprite, and the band-purity scan above. A guard test reads every registered map's committed Tiled JSON and fails if a map grows past the 1500 world px the band can sort — silent clamping would flatten the sort into a tie at the bottom of the map rather than crash. **`tests/world-depth-sorting.spec.ts` (7 browser tests) is the wiring-level gate**: the unit layer only exercises the pure helper, so a revert of the `WorldScene` / `PolishedWorldScene` / `HeroPresentationController` call sites would have left it green. The spec reads depths off the live display list of the running game for both profiles — both repaired orderings, exact agreement with the shared helper across a five-position top-to-bottom sweep, and one case that walks with the arrow key rather than teleporting. Verified **red on all 7** with the three call sites reverted to their old fixed depths (name-only changes kept, so the failures are about the sort and not a missing test handle), green with them restored. Mira's silhouette gained a display-list name (`MIRA_SILHOUETTE_NAME`) so the suite can locate the object that actually renders.

New evidence tooling (`scripts/capture-world-depth-evidence.mjs`, `scripts/build-world-depth-contact-sheet.mjs`, `scripts/world-depth-evidence-spots.mjs`) mirrors the existing Farm-scatter evidence pair and fails loudly on a missing capture or a mismatched before/after pair. ## 2026-07-24 — HUD and touch-control consolidation; Practice Slime input investigation

- Author/branch: Claude Code, `claude/hud-touch-consolidation`. Executes the accepted post-D3 queue items 6 (HUD/touch-control consolidation) and 4 (Practice Slime input-reliability investigation) from `docs/playtests/PLAYTHROUGH_UI_AUDIT_2026-07-23.md` / `CURRENT_STATE.md`, built forward from `main` at `57d6505` (PR #136 merged). One coherent input-and-interface PROTOTYPE slice.
- Scope (presentation/input only in `src/scenes/WorldScene.ts` and `src/scenes/PolishedWorldScene.ts`, plus three new Phaser-free presentation modules and the emulation test surface):
  1. **Bounded joystick activation zone** — the dynamic joystick previously engaged from a touch anywhere in the entire lower-left *quadrant* (`x ≤ GAME_WIDTH/2 && y ≥ GAME_HEIGHT/2`), claiming roughly a quarter of the playfield for input. Replaced with a bounded lower-left corner zone (`src/presentation/joystickZone.ts`: `sx(130)×sy(110)` = 260×220 game px ≈ 323×274 CSS px at 1194×834), sized to comfortably contain the joystick's own visible footprint (base radius `sx(42)`) with margin. A touch that hits any interactive fixed control (`this.input.hitTestPointer` non-empty — ACTION/STATS/mute/dialogue/prompt/Stats-CLOSE) never engages or moves the joystick. Dynamic placement within the zone, drag radius, release-stops-movement, and orientation/focus-loss reset are all preserved.
  2. **ACTION four-state control** — the button had only a momentary pressed feedback and one static alpha, matching the audit's "weak inactive/available differentiation." Added distinct inactive / available / pressed / disabled-busy states (`src/presentation/actionButtonState.ts`, a pure resolver + palette): available (bright) when dialogue is open or a nearby interactable can be triggered; disabled (dimmest) while a non-dialogue modal — learning prompt, Stats, map transition — makes a press inert; inactive otherwise; pressed is the existing squash/scale feedback composed on top. Non-touch (mouse/keyboard) sessions keep the fainter alphas. Keyboard behavior and every interaction semantic (dialogue-advance stays live) are unchanged.
  3. **HUD subordination during modals** — a single `setBusy()` setter now drives `applyHudSubordination()`, which dims (never removes) the header, objective, and hint chrome while a modal holds focus, so the guidance reads as subordinate rather than competing (audit P2). `PolishedWorldScene` overrides it to dim its own visible presentation-text layer instead of the permanently alpha-0 base objects, preserving the WorldScene-authority / PolishedWorldScene-presentation split — no authority was collapsed to reduce object count. One visible objective layer and one ambient-hint layer are retained; Grade 2 keeps READ ALOUD and both profiles keep their guidance.
  4. **Second touch pointer** — two active touch pointers are configured once, game-wide, via `input.activePointers: 2` in `gameConfig` (not `addPointer()` in a scene), so the movement thumb (lower-left joystick) and an ACTION tap (lower-right) can be down at once; Phaser tracks a single touch pointer by default, which silently made "walk and act at the same time" impossible on a tablet. Configuring it in the game config avoids growing the game-wide pointer pool each time `createTouchControls()` re-runs on a scene restart (map transition). A regression asserts `input.pointersTotal` stays fixed across WorldScene restarts.
- **Practice Slime input-reliability investigation (queue item 4): reproduced, not a defect.** Exercised the encounter through all three ordinary player input paths the audit names — keyboard Space, the on-screen ACTION control (real touch tap), and real touch under iPad emulation — inspecting actual hit-state transitions (`getPracticeSlimeEncounterSnapshot`), not animation (`tests-emulation/practice-slime-touch.spec.ts`). Deliberately spaced strikes land all three hits and complete on every path. The single-slot buffered-strike that drops rapid-mash input beyond one buffered slot is intentional anti-mash / anti-hold-to-win behavior (already documented and tested in `tests/practice-slime-encounter.spec.ts`) and matches the reported "animated but didn't advance" symptom. No deterministic ordinary-player input is lost; combat is unchanged.
- Real touch test path (Chromium iPad-emulation only): `tests-emulation/support/touch.ts` adds a genuine touch helper — Playwright `touchscreen.tap` for single ACTION taps, raw CDP `Input.dispatchTouchEvent` for drag and multi-touch (the high-level API is tap-only). `tests-emulation/touch-golden-journey.spec.ts` (Mage + Ranger) starts a profile, begins movement with a real touch-start inside the bounded joystick zone, drags far enough to produce measured player movement, releases and proves movement stops, triggers ACTION with a real touch, and triggers ACTION with a second touch while the movement touch is still active, asserting no console/page errors. New Phaser-free unit gates: `tests/unit/joystickZone.test.ts` and `tests/unit/actionButtonState.test.ts`. This is browser emulation, not physical-iPad or WebKit validation.
- Verification (exact final head): `npm run check` (exit 0); `npm run test:unit` (267/267, +9 from the two new unit files); `npm run smoke` (84/84); `npm run test:emulation` (14 tests — the golden-touch specs plus a new regression asserting the active touch-pointer count stays fixed across WorldScene restarts, the Practice-Slime-touch specs, and the existing 44px touch-target audit). One pre-existing, order-dependent flake in the unrelated `offline-pwa` service-worker suite (`activate cleanup deletes a previous build cache`) failed once in-sequence and then passed both in isolation and on a clean full re-run — no service-worker/caching/build code is touched by this PR, and CI runs the emulation job with `retries: 1`. Durable review evidence is a single Mage+Ranger contact sheet ([`docs/playtests/2026-07-24-hud-touch/hud-touch-contact-sheet.png`](playtests/2026-07-24-hud-touch/hud-touch-contact-sheet.png)) covering ordinary play, ACTION inactive/available/pressed, bounded joystick placement, dialogue, and the learning prompt (HUD subordinated, ACTION disabled) at 1194×834 via a Playwright iPad-touch context, per `VISUAL_EVIDENCE_RETENTION_POLICY.md`.

Learning bonuses are optional." hint on every frame; since the base hint returns to that same idle string constantly during ordinary play, the substitution never expired and covered the bottom hint bar for effectively the whole session, not the "several minutes" originally reported as a symptom of a much longer-lived defect.
